# Подробный конспект выполнения Самокат 1 А

Решение состоит из семи запросов Microsoft SQL Server, Excel с формулами, настоящей сводной таблицей и двумя графиками, а также аналитической записки по восьми исходным месячным графикам. Этот конспект объясняет порядок работы, смысл формул, допущения и ответы для защиты задания.

## 1 Как открыть и проверить решение

1. Откройте `output/Самокат_1_A_решение.xlsx` в Excel. Начните с листа «Итоги»: наверху период анализа, ниже показатели территорий и два топа.
2. На «Динамике» расположены недельные суммы и два согласованных по оси времени графика: оборот и доходность. W18 и W23 неполные.
3. «Недели и территории» показывает расчёты через SUMIFS. «Сводная» содержит отдельный нативный объект PivotTable: поля «Понедельник ISO», «Территория» и суммы оборота, себестоимости, потерь, складо-дней, заказов и клиенто-дней.
4. Для обновления сводной после правок в существующих 504 строках используйте Данные → Обновить всё. Формульные листы пересчитываются автоматически. При добавлении новых строк расширьте диапазоны формул и источник сводной, сейчас это Данные!A1:N505.
5. «Лист1» и «Лист2» содержат исходные значения; «Данные» объединяет их формулами. Исходный файл рядом с папкой решения не изменён.
6. «Проверки» сопоставляет расчёты с независимо рассчитанными контрольными числами Python. Нулевая разница означает согласованность на исходной выборке. После изменения данных контрольные значения обновляются повторным запуском analyze.py и сборки.
7. SQL расположен в `sql/solution.sql`. Разделитель GO понимают SSMS и sqlcmd. Для драйвера ODBC выполняйте блоки по отдельности без GO.

## 2 Что представляют исходные данные

На каждом листе по 504 записи. Период — 28 апреля — 1 июня 2020 года, 35 календарных дат, 18 территорий. Единица наблюдения — одна территория в один день. Ключ «дата + территория» уникален на каждом листе. Все 504 ключа совпали, потерь строк и размножения после объединения нет.

Не все территории присутствуют каждый день: из 630 возможных сочетаний дата–территория отсутствуют 126. Это не доказывает нулевой оборот или закрытие территории. В начале периода присутствуют 13 территорий, в конце — 18. При сравнении территорий нужно проверять число дней наблюдений. В последнюю полную неделю у Самары 4 дня, у Томска и Уфы по 1 дню; их недельная производительность зависит от трактовки отсутствующих дней.

Количество складов — состояние за день. Заказы — дневной поток. Число клиентов — дневное число, один человек может попасть в несколько дней. Поэтому сумма дневных клиентов называется «клиенто-дни», а не уникальные клиенты недели. Уникальность за неделю можно посчитать только по идентификаторам клиентов.

## 3 Объединение листов шаг за шагом

Нельзя просто поставить строки рядом: порядок строк разный. Сначала создаём составной ключ, затем проверяем его уникальность и ищем запись по ключу. В решении Лист2!F2 содержит `=A2&"|"&B2`. Разделитель исключает склеивание разных пар в одну строку. Дата хранится как числовая дата Excel, а не как текст.

На листе «Данные» столбцы A:F ссылаются на «Лист1». N2 считает совпадения ключа: `=COUNTIFS('Лист2'!$F$2:$F$505,M2)`. Только ровно одно совпадение разрешает подстановку.

Пример для складов G2:

```excel
=IF(N2=1,SUMIFS('Лист2'!$C$2:$C$505,'Лист2'!$A$2:$A$505,A2,'Лист2'!$B$2:$B$505,B2),NA())
```

SUMIFS здесь безопасен как поиск, потому что отдельно подтверждена уникальность ключа. При дубле или отсутствии строки формула выдаст #N/A, а не правдоподобный ноль. Для заказов и клиентов меняется суммируемый столбец. Такой подход не зависит от сортировки исходного листа. Возможная альтернатива в Excel — INDEX/MATCH по ключу или Power Query Merge с проверкой отношения один к одному.

Формулы приведены в международной записи, которая хранится внутри XLSX. В русской версии Excel отображаются локальные имена функций и обычно разделитель `;`: SUMIFS → СУММЕСЛИМН, COUNTIFS → СЧЁТЕСЛИМН, IF → ЕСЛИ, WEEKDAY → ДЕНЬНЕД, INDEX → ИНДЕКС, MATCH → ПОИСКПОЗ.

## 4 Недели ISO и последняя полная неделя

Неделя ISO начинается в понедельник, первая неделя года содержит 4 января. Одного номера недели недостаточно: нужны год ISO и номер либо дата понедельника.

В J2 находится понедельник: `=A2-WEEKDAY(A2,2)+1`. В K2 год ISO: `=YEAR(J2+3)`. Четверг определяет год недели. В L2 номер недели:

```excel
=INT((J2-DATE(K2,1,4)+WEEKDAY(DATE(K2,1,4),2)-1)/7)+1
```

Эта запись эквивалентна ISOWEEKNUM(A2). Сводная группируется по дате понедельника, поэтому недели разных лет не смешиваются.

Период рейтинга определяется относительно максимальной даты выгрузки, а не системной даты 2026 года. Последняя дата — понедельник 1 июня 2020. Предыдущая завершённая неделя — 25–31 мая, ISO 2020-W22. Формула начала: `=MAX('Данные'!A2:A505)-WEEKDAY(MAX('Данные'!A2:A505),2)-6`. Дата конца — начало + 6. При такой политике берётся неделя перед неделей максимальной даты, даже если максимум — воскресенье: это консервативное предположение о завершённости загрузки.

Выгрузка содержит W18 (6 дней), W19–W22 (по 7 дней), W23 (1 день). Неполную неделю нельзя сравнивать с полной по сумме оборота без поправки на число дней.

## 5 Показатели и знаменатели

Обозначим оборот R, себестоимость C, потери L, дневное число складов Wd.

| Показатель | Расчёт | Зачем так |
|---|---|---|
| Доля территории | Оборот территории / общий оборот того же периода | Один период и одна база |
| Наценка | (R − C) / C | Прибыль относительно себестоимости |
| Валовая маржа до потерь | (R − C) / R | Не путать с наценкой |
| Доходность после потерь | (R − C − L) / R | Учитывает все предоставленные потери |
| Средние склады полной недели | SUM(Wd) / 7 | Состояние нельзя суммировать как число складов |
| Оборот на склад | Недельный R / средние склады недели | Сопоставимая недельная производительность |

Доходность — принятое определение, так как в задании оно не раскрыто. Это не чистая прибыль: нет расходов на логистику, персонал, аренду и налоги. Наценка и доходность рассчитываются из общих сумм. Простое среднее дневных процентов даёт неправильный вес дням разного масштаба.

В рейтинге последней полной недели средние склады рассчитаны как складо-дни / 7 для всех территорий. Для территорий с отсутствующими днями это эквивалент числа складов за календарную неделю по наблюдаемому объёму, а не утверждение, что в пропущенные дни складов не было. На листе «Недели и территории» для описательной статистики используется среднее по числу дней с данными. Разница явно показана и позволяет увидеть чувствительность результата. У лидеров есть все 7 дней.

Деление на нулевую базу показывает «н.д.» либо #N/A в месте критического нарушения ключа. Ноль потерь при существующих продажах — допустимое значение. Неизвестный показатель не заменяется нулём.

## 6 Как устроена сводная и графики

В Excel вручную такую сводную можно построить: выделить таблицу JoinedData на «Данных» → Вставка → Сводная таблица. В строки добавить понедельник ISO, затем территорию. В значения добавить суммы оборота, себестоимости, потерь, складо-дней, заказов, клиенто-дней. Форматы денежных полей — числовой, два знака.

Для процентов используйте отношения агрегированных сумм, а не «среднее» от процентов. В решении эти расчёты открыто сохранены на формульном листе «Недели и территории». Нативная сводная поддерживает перестановку полей и обновление. Не нужно выдавать обычную таблицу SUMIFS за объект PivotTable: здесь присутствуют оба варианта.

Для динамики данные агрегируются по каждой ISO-неделе без территории. Оборот и доходность вынесены в два графика с одной временной шкалой, поскольку рубли и проценты имеют разные единицы. Диаграммы редактируются в Excel и привязаны к ячейкам, а не вставлены картинкой.

## 7 Разбор SQL запросов

### Запрос 1 Поиск товаров

Фильтр LIKE N'%самокат%' находит подстроку в любой части названия. Префикс N сохраняет кириллицу. COLLATE Cyrillic_General_100_CI_AS делает сравнение без учёта регистра независимо от настроек базы. Условие shelf_life <= 7 включает ровно 7 суток. NULL не проходит сравнение. Значения отрицательного срока годности требуют отдельной проверки качества; их нельзя молча исправлять. Начальный процент затрудняет использование обычного индекса для поиска подстроки.

### Запрос 2 Работающие склады

Склад должен открыться не позже текущей даты, а закрыться позже неё либо не иметь даты закрытия. Дата закрытия трактуется как первый нерабочий день. Если бизнес считает её последним рабочим днём, замените > на >=. GROUP BY объединяет по городу, HAVING оставляет города с числом складов строго больше 50. Условие по отдельным строкам относится к WHERE, по агрегатам — к HAVING.

### Запрос 3 Среднее число SKU

Сначала выбираются склады, активные хотя бы один день июня 2020 года. Затем COUNT(DISTINCT product_id) считает разные проданные товары каждого склада; quantity > 0 исключает строки без фактической положительной продажи. LEFT JOIN сохраняет склады без продаж, COALESCE превращает отсутствие продаж в ноль SKU. AVG считается по всем активным складам города. Это не число уникальных SKU города, делённое на склады: один и тот же SKU может продаваться на нескольких складах. Если заказчик хочет знаменатель только из продававших складов, нужен INNER JOIN; основное решение явно выбирает всю активную сеть.

### Запрос 4 Заказы и уникальные клиенты

Таблица orders имеет зерно «один заказ». COUNT_BIG(*) корректен при уникальном order_id, как заявлено структурой. COUNT(DISTINCT user_id) считает клиента один раз в каждой группе. GROUPING SETS одновременно строит месяцы по городам и по компании. Компания считается из исходных заказов: сложение клиентов городов дублировало бы людей с заказами в нескольких городах. LEFT JOIN сохраняет заказы с неизвестным складом в группе NULL, не теряя их из компании. GROUPING отличает итог компании от реального неизвестного города. Месяцы без заказов не создаются искусственно; для полного календаря нужен отдельный календарь месяцев.

### Запрос 5 Средний заказ

Берутся 14 завершённых календарных дней до текущего дня: [today − 14; today). По каждому складу считаются сумма чеков и количество заказов. Городской средний чек — SUM(сумм чеков складов) / SUM(числа заказов складов). AVG от средних складов неверен: маленький склад получает тот же вес, что большой. Оконные SUM сохраняют строку склада и добавляют городской ориентир. После расчёта отбираются склады со строго большим чеком; сортировка по имени без учёта регистра. При трактовке «последние 14 × 24 часа до текущей секунды» замените границы на GETDATE() и DATEADD(day,-14,GETDATE()).

### Запрос 6 Потери по группам

Продажи и потери сначала независимо агрегируются по паре group1 + group2 за 28 завершённых дней. Прямой JOIN двух фактов до агрегации размножил бы суммы. UNION ALL и повторная группировка сохраняют группы, присутствующие только в одном факте, включая группы с NULL в названии. Все статьи потерь включены: фильтра item_id нет. Две разные доли: потери группы / продажи группы и потери группы / все потери компании. NULLIF защищает нулевой знаменатель, возвращая NULL, а не ноль. Потери используются в предоставленной оценке amount; сопоставление потерь в себестоимости с продажами — метрика задания, не валовая маржа.

Основной запрос предполагает, что product_id всегда найден в справочнике. Для промышленной витрины сначала проверьте внешние ключи; иначе потери неизвестных товаров исчезнут из знаменателя компании. Их следует включать отдельной группой «Неизвестный товар». Наличие таких строк в реальной базе здесь проверить нельзя: таблицы SQL не предоставлены.

### Запрос 7 Два рейтинга внутри категории

Отбираются все московские склады, активные хотя бы один день мая 2021 года. Один и тот же знаменатель используется для всех товаров: так сравниваются продажи по всей сети Москвы, а не только по складам, где конкретный товар оказался представлен. Предварительные суммы продаж и потерь объединены через UNION ALL; товар с потерями без продаж не исчезает.

ROW_NUMBER с PARTITION BY group1 строит отдельный рейтинг внутри группы первого уровня. При равных суммах product_id обеспечивает воспроизводимый порядок. В результат попадают товары из топ-10 продаж ИЛИ топ-10 потерь; это объединение, не пересечение. В группе может быть до 20 строк. Дополнительно отсекаются нулевые «лидеры» по соответствующей метрике. Если бизнес требует включить всех с равной суммой на 10-м месте, следует заменить ROW_NUMBER на RANK или DENSE_RANK и согласовать различие между ними. Рейтинг строится по всем товарам с активностью в периоде, а не по неограниченному справочнику.

### Общие детали SQL

Интервалы дат полуоткрытые: >= начало и < следующий период. Это включает любое время последнего дня и не зависит от точности datetime. Не оборачиваем индексируемый столбец даты в YEAR или MONTH внутри WHERE. Для группировки такие функции допустимы.

В примерах справочника product_id = 3577634400 и user_id = 4557094039 превышают максимум INT 2147483647. Реальная схема должна использовать BIGINT. Запросы не приводят идентификаторы к INT. Предполагаются уникальные ключи справочников и заказов, согласованные поля дат и складов в order_line, заполненные денежные суммы. Проверка этих условий должна предшествовать запуску на реальной базе.

## 8 Месячная записка и ограничения интерпретации

Месячные показатели извлечены из сохранённых рядов восьми диаграмм, а не из дневной таблицы. На листе «Месячные показатели» сохранены все 13 месяцев и формулы изменения апреля к маю. Исходные ряды и их названия сохранены также в docs/monthly_series.json. Текст готовой записки находится в «Аналитическая записка.md».

Для процентов нужно различать относительный рост и процентные пункты. Потери 0,421% → 0,578% означают +0,157 п.п. и +37,31%. Для декомпозиции чека используется произведение цены и количества единиц, поэтому эффекты нельзя просто сложить без перекрёстного члена.

В графике запаса противоречат друг другу единицы названия графика и ряда. Абсолютные денежные выводы по этому показателю не делаются. Рост запаса одновременно с потерями поддерживает гипотезу проблем оборачиваемости, но не доказывает причинность. Внешние события, сезонность, промо и качество клиентского привлечения без дополнительных данных остаются гипотезами.

## 9 Короткие ответы для защиты

**Почему объединяли по двум полям?** Дата повторяется у разных территорий, территория повторяется в разные даты. Уникальна только их пара.

**Почему не сложили склады?** Сумма ежедневного состояния даёт складо-дни. Для недельного оборота на склад нужен средний размер сети за неделю.

**Почему разные топы?** Доля показывает масштаб территории, оборот на склад — интенсивность использования сети. Большая территория может лидировать по масштабу, но уступать по производительности.

**Почему не усредняли проценты?** Правильный итог — отношение сумм с экономически корректным весом, а не равный вес каждого дня или территории.

**Почему LEFT JOIN и UNION ALL?** Они сохраняют объекты без соответствующей активности в другом факте. JOIN двух детальных фактов опасен размножением строк.

**Что попросить дополнительно?** Определение доходности, правила дат открытия/закрытия, трактовку пропущенных дней, оценку запасов и потерь, реальные таблицы SQL с ключами и доступ к тестовому SQL Server.

## 10 Воспроизводимость и проверка

`src/analyze.py` читает исходник через openpyxl, проверяет ключи и независимо считает контрольные результаты. `src/build.mjs` создаёт XLSX через @oai/artifact-tool. `src/add_pivot.py` добавляет нативные части PivotTable в OOXML, поскольку экспорт сводных в используемой библиотеке ненадёжен. `src/verify.py` повторно читает итоговый файл, сверяет объединённые строки, суммы, топы, формулы, структуру сводной и графики. Данные в исходнике не меняются.

Порядок запуска: analyze.py → build.mjs → add_pivot.py → write_docs.py → sql_validate.py → verify.py. Для Node требуется @oai/artifact-tool, для Python — openpyxl и lxml. Скрипты принимают папку решения относительно своего расположения. Исходный Excel должен лежать на уровень выше. Контрольные результаты публикуются в output/summary.json и output/verification.json.

SQL Server и сами таблицы из SQL-части не предоставлены. Поэтому SQL проверен разбором синтаксиса T-SQL и выполнением на небольших синтетических примерах в DuckDB после преобразования диалекта; это не исполнение в Microsoft SQL Server. Проверка в нативном SQL Server остаётся шагом при появлении доступа. Excel проверен расчётным движком artifact-tool и повторным чтением OOXML; интерактивное обновление сводной в настольном Excel не проверено.
